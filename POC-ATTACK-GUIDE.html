Metrobank POC — Attack Demo Guide

PGC Bank demo app × Cloudflare Application Security. Every attack in this guide is launched against our own demo environment only: banking.puregroundscoffee.com — never against customer infrastructure. MacBook Pro / macOS Terminal edition.

Tab 1 — Pre-Demo Setup (MacBook Pro)

Everything here runs in the macOS Terminal app with plain curl (preinstalled on every Mac — no curl.exe, no --ssl-no-revoke, no Git Bash, no PowerShell). Work top to bottom; each step tells you exactly what success looks like.

Step 1 · What you need on the table

A MacBook Pro on a clean network (office or hotspot — see the note in UC-1 about networks that intercept uploads).
Access to the Cloudflare dashboard, account Pure Grounds Coffee Co., zone puregroundscoffee.com.
The Cloudflare API token (the same one used on the demo Windows box — it is an environment variable there named CLOUDFLARE_API_TOKEN).
Python 3 — run python3 --version first; if macOS offers to install Command Line Tools, accept.

Step 2 · Get the code

# pick any folder you like, then:
git clone https://github.com/davidrecla/banking.git
cd banking
git pull

Success looks like: ls shows attack-simulation.sh, test-api.sh, scripts/demo-edge-config.py.

Step 3 · One-time installs

curl --version          # built into macOS — any version is fine
python3 --version       # 3.9+ is fine
pip3 install pyyaml     # needed by demo-edge-config.py to parse the OpenAPI schema

Step 4 · Connect to Cloudflare

export CLOUDFLARE_API_TOKEN="paste-the-token-here"

Set it once per Terminal window (or add the line to ~/.zshrc to make it permanent). The token is a secret: never paste it into chat, screenshots, or the guide itself.

Why does a terminal demo need a Cloudflare API token? The centerpiece of the demo is flipping protection on and off live: python3 scripts/demo-edge-config.py arm turns on eight zone rules and switches schema validation from log to block in one command, and disarm puts it all back. That script is just an API client — it calls the Cloudflare API to toggle the zone's existing PGC demo: rules, and the token is how those calls authenticate. Without it you'd be clicking through the dashboard eight times mid-meeting, and the "nothing redeployed, no code changes — one command" moment wouldn't land. Read-only rehearsal: status uses the same token just to read the zone state. If a customer asks: this is the same API their own automation (Terraform, CI/CD) uses to manage Cloudflare as code.

Step 5 · Confirm the zone is staged

python3 scripts/demo-edge-config.py status

Expect exactly this (the safe, disarmed staging state): schema validation default action log, eight PGC demo: rules all [off], and the final line [on] Sensitive Data Detection ruleset (dashboard-managed, detect-only).

  • The eight rules: fallthrough block · unauthenticated internal-debug block · malicious-uploads (content scanning) block · query-string block on /api/profile · three rate limits (BOLA enumeration, express transfers, loan/investment spam) · exposed credential check on login.
  • Sensitive Data Detection stays on in both states on purpose: it scans responses and logs matches but never blocks — that visibility is UC-2's evidence.
  • If anything looks wrong: python3 scripts/demo-edge-config.py sync then ... disarm. The tool only ever touches rules prefixed PGC demo: — nothing else on the zone changes.
One-time dashboard settings (already done on this zone; verify, don't redo): Security → API Shield → Settings: session identifier = JWT sub claim. Security → Data → Sensitive Data Detection: managed ruleset deployed and enabled (this is the line status reports as [on]).

Step 6 · Load the attacker session

Paste this whole block. It logs in as the attacker's ordinary customer (chris.brown), stores the JWT in $TOKEN, and finds that user's savings-account id in $SAVINGS_ID. Every attack command in Tab 2 assumes these exist. Tokens last 24h; re-paste the block in any new Terminal window.

BASE=https://banking.puregroundscoffee.com

TOKEN=$(curl -s -X POST \
  -H 'Content-Type: application/json' \
  -d '{"username":"chris.brown","password":"cbrown123"}' \
  $BASE/api/auth/login | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

SAVINGS_ID=$(curl -s -H "Authorization: Bearer $TOKEN" \
  $BASE/api/accounts | sed -n 's/.*{"id":"\([^"]*\)"[^{]*"account_type":"savings".*/\1/p' | head -1)

echo "token loaded, savings account $SAVINGS_ID"

Success looks like: the echo prints a UUID. Note: login is capped at 5 attempts/minute per username — if you get a 429, wait a minute.

Step 7 · Rehearse end-to-end (the day before, ~15 minutes)

./test-api.sh                  # expect: 39 passed, 0 failed
./attack-simulation.sh before  # expect: every line VULNERABLE

The script prints OWASP-style labels (API1–API9); Tab 2 groups the same attacks by POC use case — same attacks, different order. Residue from the run (pending $3000 loans, $0.01 transfers) reconciles with account balances by design — nothing needs resetting.

Verification status (measured, not planned): test-api.sh 39/39 PASS · attack-simulation.sh before 11/11 VULNERABLE · after 11/11 BLOCKED · legitimate traffic re-tested while armed — all 200s · arm → disarm cycle leaves the zone cleanly staged.

Step 8 · Demo morning (2 minutes)

python3 scripts/demo-edge-config.py status — confirm the staged state from Step 5.
Paste the Step 6 bootstrap block into a fresh Terminal window.
Browser tabs open: Cloudflare dashboard → zone → Security → Events; Security → API Shield (Discovery / Web Assets); the app logged in as admin; a private window logged in as chris.brown (the attacker's UI session — the homepage upload button uses it).
If the room goes sideways at any point: python3 scripts/demo-edge-config.py disarm restores the known-good baseline in seconds.

Tab 2 — Attack Use Cases

Five use cases from the Metrobank POC plan, executed against the banking demo app. Each use case lists the Cloudflare feature it proves, the two attacks, and what to show in the dashboard. Commands assume the Tab 1 bootstrap ($TOKEN, $SAVINGS_ID).

Why are we attacking this app and not the customer's environment? Say this out loud early — it lands well with bank security teams: "We will never fire exploit traffic at your production assets, even in a POC. The use cases we already validated on your environment — bot management, managed IP lists, account-level WAF, payload inspection — were enabled and evidenced passively, on your real traffic. For the use cases that require proving an attack actually gets blocked, we built a deliberately vulnerable bank: this demo app contains nine intentional flaws mapped to the OWASP API Security Top 10, on infrastructure we own. You watch the attack succeed, then watch the same attack die at the Cloudflare edge." It also makes the result unarguable: the before/after contrast on a controlled target shows exactly what the same configuration will do in front of their APIs.
The demo flow (same for every use case): 1) run the attack — it succeeds (BEFORE = zone disarmed) → 2) python3 scripts/demo-edge-config.py arm — one command, live on camera, nothing redeployed → 3) run the same attack — it is blocked at the edge (AFTER) → 4) show the evidence in Security → Events → 5) at the very end of the meeting: python3 scripts/demo-edge-config.py disarm.

UC-1 · Content Scanning

Plan criterion: "Upload a benign file and a known-malicious sample; the malicious upload is flagged/blocked and visible in Security Events."
Feature showcasedWAF Content Scanning (malicious uploads detection; Enterprise add-on) via the staged rule PGC demo: block malicious uploads (cf.waf.content_scan.has_malicious_obj → block). Same AV engine as Cloudflare Zero Trust. Environment attackedDemo app upload path: UI button → POST /api/uploads → R2 storage (no type/size restrictions by design).
Attack 1.1 · Malicious upload from the browser (most visual)
  • Private window, logged in as chris.brown → homepage → "File uploads, scanned before they land" → upload the EICAR test file (/tmp/eicar.com, created in Attack 1.2).
  • BEFORE 201 — file lands in Documents (clean it up from the Documents page afterwards).
  • AFTER 403 — "Blocked at the Cloudflare edge" right in the app's UI.
Attack 1.2 · Malicious upload via API (exactly what the button does)
# create the industry-standard EICAR anti-malware test string (harmless):
printf '%s' 'X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*' > /tmp/eicar.com

curl -s -w "\nHTTP %{http_code}\n" -X POST \
  -H "Authorization: Bearer $TOKEN" -F "file=@/tmp/eicar.com" $BASE/api/uploads
  • BEFORE 201 + upload id (cleanup: curl -s -X DELETE -H "Authorization: Bearer $TOKEN" $BASE/api/uploads/<id>).
  • AFTER 403 from content scanning, before R2 is touched.
Dashboard beatSecurity → Events, service Content Scanning — the matched verdict per attempt.
Network caveat: if this run happens on a network whose proxy inspects uploads (e.g. a corporate Cloudflare Gateway), the file may be blocked client-side before it reaches the zone (observed as a 302 to a block page). That is the local network doing its job — switch to a clean hotspot or lead with the UI button from the same observation: any block proves the file can't reach storage.

UC-2 · Sensitive Data Detection

Plan criterion: "Trigger a test response containing sample sensitive data; a Sensitive Data Detection match is recorded in Security Events/analytics."
Feature showcasedWAF Sensitive Data Detection managed ruleset — scans HTTP responses for PII/financial patterns and logs every match (always on; detect-only, never blocks). Bonus: the same matches feed API Shield Web Assets, which labels the endpoint (cf-risk-sensitive). Environment attackedTwo endpoints that leak PII-shaped data in their responses (fake SSNs, incl. the historically-public 078-05-1120).
Attack 2.1 · Unauthenticated internal dump
curl -s $BASE/api/internal/debug | grep -o '"ssn":"[^"]*"'
  • BEFORE 200 — full user table: password hashes, salts, SSNs, auth config. No credentials needed.
  • AFTER 403 — the staged rule PGC demo: block unauthenticated /api/internal/debug kills the leak path.
Attack 2.2 · Undocumented "internal mode" on the profile endpoint
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/profile?internal=1" | grep -o '"ssn":"[^"]*"'
  • BEFORE 200 — an undocumented query param flips the endpoint to full-record mode (session payload, SSN, raw account rows).
  • AFTER 403 — PGC demo: block any query string on /api/profile; the contract declares none.
Dashboard beatSecurity → Events — matches logged by the Sensitive Data Detection service, one per leaky response. Then Security → API Shield → Web Assets — the endpoint rows carry the sensitive-data label.
Timing: event/label propagation takes minutes. Run both attacks during the BEFORE sweep (they double as UC-2's traffic generator), and show the labels from the rehearsal if the live ones lag. Talking point for the base /api/profile response, which still leaks the hash: the edge detects and blocks access paths — redacting fields inside an otherwise-valid response is the app's fix.

UC-3 · Exposed Credentials Check

Plan criterion: "Submit a test login using a known-leaked credential pair; the request is flagged and logged in Security Events."
Feature showcasedCloudflare Exposed Credentials Check managed ruleset on POST /api/auth/login (staged rule PGC demo: exposed credential check on login; off in the BEFORE state, armed with everything else). On a hit it logs a Security Event and sets the Exposed-Credential-Check header; the default action never blocks, so it can run in detect mode in production. Environment attackedThe app's JSON login endpoint — exactly the {username, password} shape the ruleset scans.
Attack 3.1 · Login with a known-pwned credential pair (credential stuffing / reuse)
curl -s -o /dev/null -w "leaked-cred login attempt -> %{http_code}\n" \
  -X POST -H 'Content-Type: application/json' \
  -d '{"username":"known.pwned.username","password":"known-pwned-password"}' \
  $BASE/api/auth/login
  • App still answers 401 (no such user) — the point is not access, it's that the edge recognized the pair from public breach corpuses.
  • BEFORE rule off — nothing recorded.
  • AFTER Security → Events, filter Service Exposed Credential Check: the attempt is there.
Attack 3.2 · Same attack through the login UI (visual beat)
  • Browser → $BASE/login → enter any genuinely pwned pair → "invalid credentials" for the user as normal — while Security Events flags the pair at the edge. Emphasize: protection is invisible to legitimate users.
Honest caveat: the check fires only on pairs actually present in the breach corpus. The seeded demo accounts are deliberately not leaked — use any real pwned pair (e.g. from haveibeenpwned) to force a hit. Position as detection + visibility that can be raised to block/managed challenge later.

UC-4 · Advanced Rate Limiting

Plan criterion: "Generate traffic exceeding the configured threshold; offending clients are throttled/blocked while legitimate traffic is unaffected; events visible in analytics."
Feature showcasedRate limiting rules on sensitive endpoints (three staged rules: express-transfer burst 10/min, BOLA-path enumeration 5 per 30s, loan/investment spam 5/min; characteristics ip.src + cf.colo.id — the same engine supports counters on any characteristic: session, header, JWT claim). Environment attackedAn express transfer endpoint with no in-app limiter, and a per-user balance endpoint with no ownership check (enumeration is inherently high-rate).
Attack 4.1 · Transfer burst — abuse of a no-limiter endpoint
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "transfer $i -> %{http_code}\n" \
    -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"fromAccountId\":\"$SAVINGS_ID\",\"toUsername\":\"sarah.johnson\",\"toAccountType\":\"savings\",\"amount\":0.01,\"note\":\"burst $i\"}" \
    $BASE/api/transfers/express
done
  • BEFORE 20 × 201 — every $0.01 transfer completes (you can show them landing in chris.brown's transaction history).
  • AFTER 403 from request #1 (path outside the API contract) — and had it been a documented path, 429 once the limit trips. Contrast: the real transfer endpoint enforces the same control in application code; here it's zero code at the edge.
Attack 4.2 · Balance enumeration (BOLA harvesting)
# gather victim ids from the debug dump (works in BEFORE), then enumerate:
IDS=$(curl -s $BASE/api/internal/debug \
  | grep -oE '"id":"[0-9a-f-]{36}"' | cut -d'"' -f4 | sort -u)
for uid in $IDS; do
  curl -s -o /dev/null -w "balance $uid -> %{http_code}\n" \
    -H "Authorization: Bearer $TOKEN" $BASE/api/users/$uid/balance
done
  • BEFORE every customer's balance, harvested in seconds by one ordinary user.
  • AFTER 403 on each request (undocumented path) and/or 429 when the enumeration rate limit trips at 5 per 30s — enumeration dies either way. Re-run ./test-api.sh while armed: 39/39 green — legitimate users untouched.
Dashboard beatSecurity → Events, last 15 minutes — every throttled/blocked request named by rule. Forward-looking pair: Volumetric Abuse Detection learns per-endpoint baselines and recommends limits automatically (needs weeks of production traffic — positioned, not demoed). Optional extraLoan-application spam: 8 rapid POST /api/loans/apply ($2000 each, all auto-pending) → after: five 201s then 429s (5/min rule).

UC-5 · API Shield: Discovery + Schema Validation

Plan criterion (optional use case): "Enable API Discovery to inventory API endpoints; apply Schema Validation to reject non-conforming requests; valid requests pass; events logged."
Feature showcasedAPI Discovery (finds operations in live traffic, incl. shadow APIs) · Schema Validation (uploaded OpenAPI contract, log→block; strict typing rejects malformed bodies) · fallthrough rule (cf.api_gateway.fallthrough_detected — anything not in the contract is hostile) · session identifier = JWT sub. Environment attackedA deprecated v1 endpoint that was never decommissioned, and a debug endpoint that explodes on malformed JSON.
Attack 5.1 · The shadow API
curl -s -H "Authorization: Bearer $TOKEN" $BASE/api/v1/accounts
# and the never-removed cross-user override on it:
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/accounts?userId=f49a7d79-e6dc-4c91-ba4a-5d62be9f81e7"
  • BEFORE 200 — undocumented verbose rows, plus other users' data via the override.
  • Security → API Shield → Discovery: GET /api/v1/accounts listed as an operation absent from the uploaded schema — the shadow API, found without any agent or config.
  • AFTER 403 — fallthrough rule blocks every operation outside the contract.
Attack 5.2 · Malformed payload — the error-surface attack
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{not json' $BASE/api/debug/parse
  • BEFORE 500 with a JavaScript stack trace and internal file paths — recon gold.
  • AFTER 403/400 at the edge — schema strict typing + fallthrough: garbage never reaches the app, so there's no error surface to mine.
Optional extras Privilege escalation that moves money (apply $3000 → POST /api/admin/loans/<id>/force-approve as a regular user: before it disburses, after 403 — refresh chris.brown's dashboard for the money shot) · excessive-data-exposure talking point on base /api/profile · oversized JSON body to /api/transfers/batch → automatic 413 plan-tier body limit.
Wrap-up beats: with protections still armed, re-run ./test-api.sh → 39/39 (legitimate traffic untouched). Then python3 scripts/demo-edge-config.py disarm so the zone returns to staged. Forward-looking: ML posture features — BOLA enumeration risk labels, Volumetric Abuse recommendations — accrue over weeks of production traffic; today showed the deterministic layer.
