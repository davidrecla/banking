Metrobank POC — Attack Demo Guide

PGC Bank demo app × Cloudflare Application Security. Attacks run from a MacBook Terminal (script/curl) against our own demo app only — banking.puregroundscoffee.com, never customer infrastructure. Every protection is enabled in the Cloudflare dashboard, live, with the customer.

Tab 1 — Pre-Demo Setup (MacBook Pro)

Two halves to prepare: a Terminal for running the attacks, and the Cloudflare dashboard where every protection gets toggled live during the session. No API tokens, no config scripts in this guide — the customer sees each control exactly where their own admins would use it.

Step 1 · What you need on the table

A MacBook Pro on a clean network (office or hotspot — see the note in UC-1 about networks that intercept uploads).
Access to the Cloudflare dashboard, account Pure Grounds Coffee Co., zone puregroundscoffee.com.
Terminal: open Spotlight (⌘+Space), type Terminal, press Enter.

Step 4 · Load the attacker session (Terminal)

Paste this whole block. It logs in as the attacker's ordinary customer (chris.brown), stores the JWT in $TOKEN, and finds that user's savings-account id in $SAVINGS_ID. Every attack command in Tab 2 assumes these exist. Tokens last 24h; re-paste the block in any new Terminal window.

BASE=https://banking.puregroundscoffee.com

TOKEN=$(curl -s -X POST \
  -H 'Content-Type: application/json' \
  -d '{"username":"chris.brown","password":"cbrown123"}' \
  $BASE/api/auth/login | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

SAVINGS_ID=$(curl -s -H "Authorization: Bearer $TOKEN" \
  $BASE/api/accounts | sed -n 's/.*{"id":"\([^"]*\)"[^{]*"account_type":"savings".*/\1/p' | head -1)

echo "token loaded, savings account $SAVINGS_ID"

Success looks like: the echo prints a UUID. Note: login is capped at 5 attempts/minute per username — if you get a 429, wait a minute.

Step 5 · Rehearse end-to-end (the day before, ~20 minutes)

./test-api.sh                  # expect: 39 passed, 0 failed
./attack-simulation.sh before  # expect: every line VULNERABLE

Then arm every toggle from Step 3 in the dashboard (this doubles as your click-path rehearsal) and run ./attack-simulation.sh after — expect every line BLOCKED. Finish by returning every toggle to the staging state (all rules Off, schema validation Log). The script prints OWASP-style labels (API1–API9); Tab 2 groups the same attacks by POC use case — same attacks, different order. Residue from runs (pending $3000 loans, $0.01 transfers) reconciles with account balances by design — nothing needs resetting.

Verification status (measured, not planned): test-api.sh 39/39 PASS · attack-simulation.sh before 11/11 VULNERABLE · after 11/11 BLOCKED · legitimate traffic re-tested while armed — all 200s.

Step 6 · Demo morning (2 minutes)

Dashboard: re-walk the Step 3 table — everything Off, schema at Log.
Paste the Step 4 bootstrap block into a fresh Terminal window.
Browser tabs open: zone → Security → Events; Security → API Shield (Discovery / Web Assets); Security → WAF (your toggling station for the meeting); the app logged in as admin; a private window logged in as chris.brown (the attacker's UI session — the homepage upload button uses it).
If the room goes sideways: the staging state is just "everything in the Step 3 table Off" — you can always get back in under a minute.

Tab 2 — Attack Use Cases

Five use cases from the Metrobank POC plan, executed against the banking demo app. Each use case lists the Cloudflare feature it proves, the two attacks, and the exact dashboard toggle you flip — live, with the customer — to make the same attack fail. Commands assume the Tab 1 bootstrap ($TOKEN, $SAVINGS_ID).

Why are we attacking this app and not the customer's environment? Say this out loud early — it lands well with bank security teams: "We will never fire exploit traffic at your production assets, even in a POC. The use cases we already validated on your environment — bot management, managed IP lists, account-level WAF, payload inspection — were enabled and evidenced passively, on your real traffic. For the use cases that require proving an attack actually gets blocked, we built a deliberately vulnerable bank: this demo app contains nine intentional flaws mapped to the OWASP API Security Top 10, on infrastructure we own. You'll watch each attack succeed, then we'll arm the control in the dashboard — the same screen your admins use — and watch the same attack die at the edge."
The demo flow (per use case): 1) run the attack from the Terminal — it succeeds (BEFORE = rule Off) → 2) open the card's Arm in the dashboard toggle and switch it On, with the customer following along → 3) run the same attack — it is blocked at the edge (AFTER) → 4) show the evidence in Security → Events → 5) after UC-5, re-run the full script (./attack-simulation.sh after) as the finale — everything blocked — then return every toggle to Off and schema validation to Log before you leave the room.

UC-1 · Content Scanning

Plan criterion: "Upload a benign file and a known-malicious sample; the malicious upload is flagged/blocked and visible in Security Events."
Feature showcasedWAF Content Scanning (malicious uploads detection; Enterprise add-on). Same AV engine as Cloudflare Zero Trust. Environment attackedDemo app upload path: UI button → POST /api/uploads → R2 storage (no type/size restrictions by design).
Attack 1.1 · Malicious upload from the browser (most visual)
  • Private window, logged in as chris.brown → homepage → "File uploads, scanned before they land" → upload the EICAR test file (/tmp/eicar.com, created in Attack 1.2).
  • BEFORE 201 — file lands in Documents (clean it up from the Documents page afterwards).
  • AFTER 403 — "Blocked at the Cloudflare edge" right in the app's UI.
Attack 1.2 · Malicious upload via API (exactly what the button does)
# create the industry-standard EICAR anti-malware test string (harmless):
printf '%s' 'X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*' > /tmp/eicar.com

curl -s -w "\nHTTP %{http_code}\n" -X POST \
  -H "Authorization: Bearer $TOKEN" -F "file=@/tmp/eicar.com" $BASE/api/uploads
  • BEFORE 201 + upload id (cleanup: curl -s -X DELETE -H "Authorization: Bearer $TOKEN" $BASE/api/uploads/<id>).
  • AFTER 403 from content scanning, before R2 is touched.
Arm in the dashboard
Security → WAF → Custom rules → PGC demo: block malicious uploads (content scanning) → toggle On. Point at the expression while you're there: cf.waf.content_scan.has_malicious_obj — one rule a customer admin writes in a minute.
Dashboard beatSecurity → Events, service Content Scanning — the matched verdict per attempt.
Network caveat: if this run happens on a network whose proxy inspects uploads (e.g. a corporate Cloudflare Gateway), the file may be blocked client-side before it reaches the zone (observed as a 302 to a block page). That is the local network doing its job — switch to a clean hotspot or lead with the UI button: any block proves the file can't reach storage.

UC-2 · Sensitive Data Detection

Plan criterion: "Trigger a test response containing sample sensitive data; a Sensitive Data Detection match is recorded in Security Events/analytics."
Feature showcasedWAF Sensitive Data Detection managed ruleset — scans HTTP responses for PII/financial patterns and logs every match (always on; detect-only, never blocks). Bonus: the same matches feed API Shield Web Assets, which labels the endpoint (cf-risk-sensitive). Environment attackedTwo endpoints that leak PII-shaped data in their responses (fake SSNs, incl. the historically-public 078-05-1120).
Attack 2.1 · Unauthenticated internal dump
curl -s $BASE/api/internal/debug | grep -o '"ssn":"[^"]*"'
  • BEFORE 200 — full user table: password hashes, salts, SSNs, auth config. No credentials needed.
  • AFTER 403 — the leak path is dead.
Attack 2.2 · Undocumented "internal mode" on the profile endpoint
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/profile?internal=1" | grep -o '"ssn":"[^"]*"'
  • BEFORE 200 — an undocumented query param flips the endpoint to full-record mode (session payload, SSN, raw account rows).
  • AFTER 403 — the contract declares no query string at all on this path.
Arm in the dashboard
The detection ruleset itself stays On at all times (Security → Data → Sensitive Data Detection) — that's what logged every leak you just generated. What you arm here are the access-path blocks:
Security → WAF → Custom rules → toggle On both PGC demo: block unauthenticated /api/internal/debug and PGC demo: block any query string on /api/profile.
Dashboard beatSecurity → Events — matches logged by the Sensitive Data Detection service, one per leaky response. Then Security → API Shield → Web Assets — the endpoint rows carry the sensitive-data label.
Timing: event/label propagation takes minutes. Run both attacks early (they seed UC-2's evidence), and show the labels from the rehearsal if the live ones lag. Talking point for the base /api/profile response, which still leaks the hash: the edge detects and blocks access paths — redacting fields inside an otherwise-valid response is the app's fix.

UC-3 · Exposed Credentials Check

Plan criterion: "Submit a test login using a known-leaked credential pair; the request is flagged and logged in Security Events."
Feature showcasedCloudflare Exposed Credentials Check managed ruleset on POST /api/auth/login. On a hit it logs a Security Event and sets the Exposed-Credential-Check header; the default action never blocks, so it can run in detect mode in production. Environment attackedThe app's JSON login endpoint — exactly the {username, password} shape the ruleset scans.
Attack 3.1 · Login with a known-pwned credential pair (credential stuffing / reuse)
curl -s -o /dev/null -w "leaked-cred login attempt -> %{http_code}\n" \
  -X POST -H 'Content-Type: application/json' \
  -d '{"username":"known.pwned.username","password":"known-pwned-password"}' \
  $BASE/api/auth/login
  • App still answers 401 (no such user) — the point is not access, it's that the edge recognized the pair from public breach corpuses.
  • BEFORE deployment off — nothing recorded.
  • AFTER Security → Events, filter Service Exposed Credential Check: the attempt is there.
Attack 3.2 · Same attack through the login UI (visual beat)
  • Browser → $BASE/login → enter any genuinely pwned pair → "invalid credentials" for the user as normal — while Security Events flags the pair at the edge. Emphasize: protection is invisible to legitimate users.
Arm in the dashboard
Security → WAF → Managed rules → deployment PGC demo: exposed credential check on login → toggle On. (Confirm the exact placement during the Step 5 rehearsal — managed-ruleset deployments list with the other managed entries.)
Honest caveat: the check fires only on pairs actually present in the breach corpus. The seeded demo accounts are deliberately not leaked — use any real pwned pair (e.g. from haveibeenpwned) to force a hit. Position as detection + visibility that can be raised to block/managed challenge later.

UC-4 · Advanced Rate Limiting

Plan criterion: "Generate traffic exceeding the configured threshold; offending clients are throttled/blocked while legitimate traffic is unaffected; events visible in analytics."
Feature showcasedRate limiting rules on sensitive endpoints (express-transfer burst 10/min, BOLA-path enumeration 5 per 30s; characteristics ip.src + cf.colo.id — the same engine supports counters on any characteristic: session, header, JWT claim). Environment attackedAn express transfer endpoint with no in-app limiter, and a per-user balance endpoint with no ownership check (enumeration is inherently high-rate).
Attack 4.1 · Transfer burst — abuse of a no-limiter endpoint
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "transfer $i -> %{http_code}\n" \
    -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"fromAccountId\":\"$SAVINGS_ID\",\"toUsername\":\"sarah.johnson\",\"toAccountType\":\"savings\",\"amount\":0.01,\"note\":\"burst $i\"}" \
    $BASE/api/transfers/express
done
  • BEFORE 20 × 201 — every $0.01 transfer completes (show a few landing in chris.brown's transaction history).
  • AFTER ten 201s, then 429s — this is a pure rate-limit block: with only the rate limit armed, nothing else stands in the way. Contrast: the app's real transfer endpoint enforces the same control in code; here it's zero code at the edge.
Attack 4.2 · Balance enumeration (BOLA harvesting)
# gather victim ids from the debug dump (run UC-2's Attack 2.1 first), then enumerate:
IDS=$(curl -s $BASE/api/internal/debug \
  | grep -oE '"id":"[0-9a-f-]{36}"' | cut -d'"' -f4 | sort -u)
for uid in $IDS; do
  curl -s -o /dev/null -w "balance $uid -> %{http_code}\n" \
    -H "Authorization: Bearer $TOKEN" $BASE/api/users/$uid/balance
done
  • BEFORE every customer's balance, harvested in seconds by one ordinary user.
  • AFTER 5 reads per 30 seconds, then 429 with a 60-second timeout — enumeration slowed to uselessness. Be precise here: rate limiting throttles the harvest; UC-5's schema contract removes the path entirely (it's an undocumented op). Re-run ./test-api.sh while armed: 39/39 green — legitimate users untouched.
Arm in the dashboard
Security → WAF → Rate limiting rules → toggle On PGC demo: express-transfer burst rate limit and PGC demo: BOLA enumeration rate limit. Show the counting expression while you're there — ip.src + cf.colo.id, 10 requests in 60s — and say it can just as easily count per session token or API key.
Dashboard beatSecurity → Events, last 15 minutes — every throttled request named by rule. Forward-looking pair: Volumetric Abuse Detection learns per-endpoint baselines and recommends limits automatically (needs weeks of production traffic — positioned, not demoed). Optional extraLoan-application spam: 8 rapid POST /api/loans/apply ($2000 each, all auto-pending) → arm PGC demo: loan/investment spam rate limit too and watch five 201s then 429s (5/min rule).

UC-5 · API Shield: Discovery + Schema Validation

Plan criterion (optional use case): "Enable API Discovery to inventory API endpoints; apply Schema Validation to reject non-conforming requests; valid requests pass; events logged."
Feature showcasedAPI Discovery (finds operations in live traffic, incl. shadow APIs) · Schema Validation (uploaded OpenAPI contract, Log → Block; strict typing rejects malformed bodies) · the fallthrough rule (cf.api_gateway.fallthrough_detected — anything not in the contract is hostile) · session identifier = JWT sub. Environment attackedA deprecated v1 endpoint that was never decommissioned, and a debug endpoint that explodes on malformed JSON.
Attack 5.1 · The shadow API
curl -s -H "Authorization: Bearer $TOKEN" $BASE/api/v1/accounts
# and the never-removed cross-user override on it:
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/accounts?userId=f49a7d79-e6dc-4c91-ba4a-5d62be9f81e7"
  • BEFORE 200 — undocumented verbose rows, plus other users' data via the override.
  • Security → API Shield → Discovery: GET /api/v1/accounts listed as an operation absent from the uploaded schema — the shadow API, found without any agent or config.
  • AFTER 403 — fallthrough rule blocks every operation outside the contract.
Attack 5.2 · Malformed payload — the error-surface attack
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{not json' $BASE/api/debug/parse
  • BEFORE 500 with a JavaScript stack trace and internal file paths — recon gold.
  • AFTER 403/400 at the edge — schema strict typing + fallthrough: garbage never reaches the app, so there's no error surface to mine.
Arm in the dashboard
Two moves, both worth narrating: ① Security → API Shield → Schema Validation → default action Log → Block ("the uploaded OpenAPI contract is now enforced"). ② Security → WAF → Custom rules → PGC demo: fallthrough block (ops outside the OpenAPI schema) → On ("and anything the contract doesn't mention is assumed hostile").
FinaleWith everything now armed: ./attack-simulation.sh after — every line BLOCKED — then ./test-api.sh → 39/39, legitimate traffic untouched. That's the whole story in two commands. Optional extras Privilege escalation that moves money (apply $3000 → POST /api/admin/loans/<id>/force-approve as a regular user: before it disburses, after 403 — refresh chris.brown's dashboard for the money shot) · excessive-data-exposure talking point on base /api/profile · oversized JSON body to /api/transfers/batch → automatic 413 plan-tier body limit.
Leave the zone staged: before you close — all 8 PGC demo: toggles back Off + schema validation back to Log (the Step 3 table). Forward-looking close: ML posture features — BOLA enumeration risk labels, Volumetric Abuse recommendations — accrue over weeks of production traffic; today showed the deterministic layer.
