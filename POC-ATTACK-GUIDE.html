Metrobank POC — Attack Demo Guide

PGC Bank demo app × Cloudflare Application Security. Attacks run from a MacBook Terminal (script/curl) against our own demo app only — banking.puregroundscoffee.com, never customer infrastructure. Every protection is enabled in the Cloudflare dashboard, live, with the customer.

Tab 1 — Pre-Demo Setup (MacBook Pro)

Two halves to prepare: a Terminal for running the attacks, and the Cloudflare dashboard where every protection gets toggled live during the session. No API tokens, no config scripts in this guide — the customer sees each control exactly where their own admins would use it.

A MacBook Pro on a clean network (office or hotspot — see the note in UC-1 about networks that intercept uploads).
Access to the Cloudflare dashboard, account Pure Grounds Coffee Co., zone puregroundscoffee.com.
Terminal: open Spotlight (⌘+Space), type Terminal, press Enter.

Step 4 · Load the attacker session (Terminal)

Every attack in Tab 2 runs as a logged-in customer — chris.brown, an ordinary Regular user. One command does it all (run it from the repo folder):

source scripts/load-attacker.sh

Success looks like: 

attacker session loaded: chris.brown @ https://banking.puregroundscoffee.com
  savings account: 00a22052-b771-…(a UUID)
  extra terminals: source /tmp/pgc-attacker.env
  token expires in 24h — source this script again tomorrow

What that one command does

  • Logs in as chris.brown with his password and stores the returned session token (a JWT — a 24-hour "key card"; from here on you show the card, not the password) as $TOKEN.
  • Looks up his savings account id and stores it as $SAVINGS_ID — money-moving attacks need a destination account.
  • Sets $BASE (the app URL) so the commands can just write $BASE/api/….
  • Saves all three to /tmp/pgc-attacker.env — a second Terminal window can skip the login entirely with source /tmp/pgc-attacker.env.
Two things beginners trip on:
① The source matters — running bash scripts/load-attacker.sh prints a reminder and exits, because variables set in a sub-shell die with it. Open a new Terminal window? Run source /tmp/pgc-attacker.env there (no re-login, respects the 5-per-minute login cap).
② The token expires after 24 hours — source scripts/load-attacker.sh again the next day.

If the script ever misbehaves, the manual fallback is: TOKEN=$(<curl login with username/password JSON>) then SAVINGS_ID=$(<curl /api/accounts with the Bearer header, extract the savings id>) — the script is exactly those two curls plus printing; read it with cat scripts/load-attacker.sh. Note there is no permanent token by design: the app mints a fresh 24h key card per login, and a never-expiring credential would be a real vulnerability in the very app we're presenting.

Step 5 · Rehearse end-to-end (the day before, ~20 minutes)

Two scripts do the rehearsal. You don't need to read or edit them — you run them and read their output. Both are just sequences of the same kind of curl calls you made by hand in Step 4. Both reuse the session from Step 4 (source scripts/load-attacker.sh) instead of logging in again — run Step 4 first and you'll see session token reused in their output; if nothing is loaded they log in on their own as a fallback. (The login endpoint caps at 5 attempts/minute per user — reuse keeps you far under it.)

Script 1 — ./test-api.sh (the "legitimate customer" check)

./test-api.sh

What it does: walks every legitimate API endpoint as chris.brown and checks the app responds correctly — 39 checks in one run. It's deliberately gentle:

  • Read checks (list accounts, transactions, cards, …) expect HTTP 200.
  • Write checks send an empty body on purpose and expect HTTP 400 ("bad request") — enough to prove the endpoint works without creating junk data.
  • The few real mutations clean up after themselves: it creates a payee and deletes it, uploads a file and deletes it, freezes and un-freezes an account. You can run it as often as you like.

How to read the output: every check prints one line starting with PASS (good) or FAIL … (expected 200, got 403) (bad — the parenthesis tells you what it wanted vs. what happened). At the end: === Summary: 39 passed, 0 failed, 0 skipped ===. Anything but 39 passed means stop and fix before demo day — most common cause: you rehearsed with protections still armed, which turns some of these into edge-blocked 403s.

Why it matters in the POC: this is your "don't break the bank" proof. After the protections are armed live, you re-run this to show the customer's real customers would never notice them.

Script 2 — ./attack-simulation.sh (the "attacker" check)

./attack-simulation.sh before

What it does: logs in as the attacker and runs all nine exploit techniques against the app — dumping the user table, calling a forgotten v1 API, force-approving a loan as a regular user, harvesting everyone's balances, and so on. The word before sets the expectation: with protections Off, every attack should succeed.

How to read the output: each attack prints one line:

  • VULNERABLE API5 force-approve (pending $3000 loan approved+disbursed…) — the attack worked. In a before run, every line should say this. That's the point: you've proven the holes are real.
  • BLOCKED API5 force-approve (403…) — the edge stopped it. This is what an after run (./attack-simulation.sh after, with everything armed in the dashboard) should print for every line.
  • UNEXPECTED / NOT-BLOCKED — something is off (a toggle in the wrong state). Fix before demo day.

Labels are OWASP-style (API1…API9); Tab 2 groups the same attacks by POC use case instead — same attacks, just presented in the customer's language. Damage is contained by design: the burst transfers move $0.01, the fraudulent loan is created by the script itself and the app keeps such loans in review, and every run's residue reconciles with account balances — nothing ever needs cleanup.

The full rehearsal loop

./test-api.sh                  # expect: 39 passed, 0 failed
./attack-simulation.sh before  # expect: every line VULNERABLE

Then arm every toggle from Step 3 in the dashboard (this doubles as your click-path rehearsal for Steps 3.2–3.5) and run:

./attack-simulation.sh after   # expect: every line BLOCKED
./test-api.sh                  # armed, still: 39 passed, 0 failed

Finish by returning the zone to staging: every PGC demo: toggle Off, schema validation back to Log (Step 3's one-line checklist).

Verification status (measured, not planned): test-api.sh 39/39 PASS · attack-simulation.sh before 11/11 VULNERABLE · after 11/11 BLOCKED · legitimate traffic re-tested while armed — all 200s.

Tab 2 — Attack Use Cases

Five use cases from the Metrobank POC plan, executed against the banking demo app. Each use case lists the Cloudflare feature it proves, the two attacks, and the exact dashboard toggle you flip — live, with the customer — to make the same attack fail.

Before any attack command: from the repo folder, run source scripts/load-attacker.sh — that one line gives this Terminal the attacker session ($BASE, $TOKEN, $SAVINGS_ID). New window? source /tmp/pgc-attacker.env restores it without re-logging in.
Why are we attacking this app and not the customer's environment? Say this out loud early — it lands well with bank security teams: "We will never fire exploit traffic at your production assets, even in a POC. The use cases we already validated on your environment — bot management, managed IP lists, account-level WAF, payload inspection — were enabled and evidenced passively, on your real traffic. For the use cases that require proving an attack actually gets blocked, we built a deliberately vulnerable bank: this demo app contains nine intentional flaws mapped to the OWASP API Security Top 10, on infrastructure we own. You'll watch each attack succeed, then we'll arm the control in the dashboard — the same screen your admins use — and watch the same attack die at the edge."
The demo flow (per use case): 1) run the attack from the Terminal — it succeeds (BEFORE = rule Off) → 2) open the card's Arm in the dashboard toggle and switch it On, with the customer following along → 3) run the same attack — it is blocked at the edge (AFTER) → 4) show the evidence in Security → Events → 5) after UC-5, re-run the full script (./attack-simulation.sh after) as the finale — everything blocked — then return every toggle to Off and schema validation to Log before you leave the room.

curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/profile?internal=1" | grep -o '"ssn":"[^"]*"'

Blocked bycustom rule PGC demo: block any query string on /api/profile.

UC-3 · Leaked Credentials Detection renamed feature

Plan criterion: "Submit a test login using a known-leaked credential pair; the request is flagged/challenged and logged in Security Events." (The plan says "Exposed Credentials Rules" — Cloudflare has replaced that managed ruleset with leaked credential detection + a mitigation rule; that is what this UC demonstrates.)
Feature showcasedLeaked credential detection — Cloudflare hashes submitted credentials and compares them against its breach database (never stores plaintext), populating cf.waf.credential_check.username_and_password_leaked on matching requests. Mitigation here is the custom rule Leaked Credentials Rule (Block when that field is true) — better than the plan's "flag": the attack never reaches the app. Environment attackedThe app's JSON login endpoint — exactly the {username, password} shape the detection scans (JSON logins are covered by default; no custom detection location needed).
Attack 3.1 · Login with breached credentials (credential stuffing / password reuse)
Terminal: uses $BASE only — no token (the point is logging in with a stolen pair). $BASE comes from source scripts/load-attacker.sh
curl -s -o /dev/null -w "leaked-cred login attempt -> %{http_code}\n" \
  -X POST -H 'Content-Type: application/json' \
  -d '{"username":"CF_EXPOSED_USERNAME","password":"CF_EXPOSED_PASSWORD"}' \
  $BASE/api/auth/login
  • CF_EXPOSED_USERNAME / CF_EXPOSED_PASSWORD are Cloudflare's official test credentials — guaranteed breach-corpus hits, so this demo is deterministic. No hunting for real pwned pairs (a genuinely pwned pair, e.g. from haveibeenpwned, works just as well if you prefer).
  • BEFORE (rule toggled Off): request flows to the app → 401 "invalid credentials" — the stolen pair sails straight through.
  • AFTER (rule On): 403 at the edge — the request never reaches the app. Security → Events shows the block, rule Leaked Credentials Rule.
Blocked bycustom rule Leaked Credentials Rule (Block on cf.waf.credential_check.username_and_password_leaked), fed by the Leaked credential detection toggle under Security → Settings → Detection tools. The event in Security Events names the rule.
Attack 3.2 · Same attack through the login UI (visual beat)
browser only — no Terminal needed
  • Browser → $BASE/login → enter the same test pair: with the rule Off it fails as a normal bad login; with the rule On the edge blocks it outright. Emphasize: the protection fires only when the submitted pair is known-breached — legitimate users see zero change.
Blocked bysame rule as 3.1: Leaked Credentials Rule — the UI login posts to the same endpoint, so the same policy catches it.
Arm in the dashboard
  1. Sidebar: Security → WAF → Custom rules tab.
  2. Find Leaked Credentials Rule — toggle Off for the BEFORE attack, then back On for the AFTER attack. (It's zone-wide on purpose: say out loud that one rule now protects every property on the zone.)
  3. Show Security → Settings → Detection tools → Leaked credential detection = On: that's the one switch that turns the whole capability on; the rule just decides what happens on a hit (Block — could also be Challenge or log-only).
Witness the detection, not just the block: rule-off runs still get detected (fields populate) — they're just allowed through. As a bonus beat, Security Analytics flags those leaked-credential attempts even when no rule blocks them, which is exactly the detect-first-then-mitigate rollout story for production.

UC-4 · Advanced Rate Limiting

Plan criterion: "Generate traffic exceeding the configured threshold; offending clients are throttled/blocked while legitimate traffic is unaffected; events visible in analytics."
Feature showcasedRate limiting rules on sensitive endpoints (express-transfer burst 10/min, BOLA-path enumeration 5 per 30s; characteristics ip.src + cf.colo.id — the same engine supports counters on any characteristic: session, header, JWT claim). Environment attackedAn express transfer endpoint with no in-app limiter, and a per-user balance endpoint with no ownership check (enumeration is inherently high-rate).
Attack 4.1 · Transfer burst — abuse of a no-limiter endpoint
Terminal: uses $TOKEN, $SAVINGS_ID, $BASE — all three come from source scripts/load-attacker.sh
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "transfer $i -> %{http_code}\n" \
    -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"fromAccountId\":\"$SAVINGS_ID\",\"toUsername\":\"sarah.johnson\",\"toAccountType\":\"savings\",\"amount\":0.01,\"note\":\"burst $i\"}" \
    $BASE/api/transfers/express
done
  • BEFORE 20 × 201 — every $0.01 transfer completes (show a few landing in chris.brown's transaction history).
  • AFTER ten 201s, then 429s — this is a pure rate-limit block: with only the rate limit armed, nothing else stands in the way. Contrast: the app's real transfer endpoint enforces the same control in code; here it's zero code at the edge.
Blocked byrate limiting rule PGC demo: express-transfer burst rate limit (10 requests/60s → 429, 120s timeout). Note: after UC-5 arms the fallthrough rule, this path also 403s outright — the 429 pure rate-limit story works while fallthrough is still Off.
Attack 4.2 · Balance enumeration (BOLA harvesting)
Terminal: uses $TOKEN, $BASE — from source scripts/load-attacker.sh
# gather victim ids from the debug dump (run UC-2's Attack 2.1 first), then enumerate:
IDS=$(curl -s $BASE/api/internal/debug \
  | grep -oE '"id":"[0-9a-f-]{36}"' | cut -d'"' -f4 | sort -u)
for uid in $IDS; do
  curl -s -o /dev/null -w "balance $uid -> %{http_code}\n" \
    -H "Authorization: Bearer $TOKEN" $BASE/api/users/$uid/balance
done
  • BEFORE every customer's balance, harvested in seconds by one ordinary user.
  • AFTER 5 reads per 30 seconds, then 429 with a 60-second timeout — enumeration slowed to uselessness. Be precise here: rate limiting throttles the harvest; UC-5's schema contract removes the path entirely (it's an undocumented op). Re-run ./test-api.sh while armed: 39/39 green — legitimate users untouched.
Blocked byrate limiting rule PGC demo: BOLA enumeration rate limit (5 requests/30s → 429, 60s timeout). After UC-5 is armed, custom rule PGC demo: fallthrough block 403s the path entirely.
Arm in the dashboard
  1. Sidebar: Security → WAF → Rate limiting rules tab.
  2. Set On: PGC demo: express-transfer burst rate limit.
  3. Set On: PGC demo: BOLA enumeration rate limit.
  4. Open either rule and show the counting expression: ip.src + cf.colo.id, 10 requests in 60s — then say it can just as easily count per session token, header, or JWT claim.

UC-5 · API Shield: Discovery + Schema Validation

Plan criterion (optional use case): "Enable API Discovery to inventory API endpoints; apply Schema Validation to reject non-conforming requests; valid requests pass; events logged."
Feature showcasedAPI Discovery (finds operations in live traffic, incl. shadow APIs) · Schema Validation (uploaded OpenAPI contract, Log → Block; strict typing rejects malformed bodies) · the fallthrough rule (cf.api_gateway.fallthrough_detected — anything not in the contract is hostile) · session identifier = JWT sub. Environment attackedA deprecated v1 endpoint that was never decommissioned, and a debug endpoint that explodes on malformed JSON.
Attack 5.1 · The shadow API
Terminal: uses $TOKEN, $BASE — from source scripts/load-attacker.sh
curl -s -H "Authorization: Bearer $TOKEN" $BASE/api/v1/accounts
# and the never-removed cross-user override on it:
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/accounts?userId=f49a7d79-e6dc-4c91-ba4a-5d62be9f81e7"
  • BEFORE 200 — undocumented verbose rows, plus other users' data via the override.
  • Security → API Shield → Discovery: GET /api/v1/accounts listed as an operation absent from the uploaded schema — the shadow API, found without any agent or config.
  • AFTER 403 — fallthrough rule blocks every operation outside the contract.
Blocked bycustom rule PGC demo: fallthrough block (ops outside the OpenAPI schema) on cf.api_gateway.fallthrough_detected — this is what "the contract is enforced" looks like as a rule. In Events the event names this rule; API Shield → Discovery is where the shadow op was first spotted.
Attack 5.2 · Malformed payload — the error-surface attack
Terminal: uses $TOKEN, $BASE — from source scripts/load-attacker.sh
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{not json' $BASE/api/debug/parse
  • BEFORE 500 with a JavaScript stack trace and internal file paths — recon gold.
  • AFTER 403/400 at the edge — schema strict typing + fallthrough: garbage never reaches the app, so there's no error surface to mine.
Blocked byschema validation (default action Block on the openapi-schema contract — Security → API Shield → Schema Validation) rejects the malformed body; the fallthrough custom rule is the alternate catcher since /api/debug/parse is undocumented. The Security Events row names whichever matched.
Arm in the dashboard
  1. Sidebar: Security → API Shield → Schema Validation → change the default action from Log to Block. Say: "the uploaded OpenAPI contract is now enforced."
  2. Sidebar: Security → WAF → Custom rules tab → set On: PGC demo: fallthrough block (ops outside the OpenAPI schema). Say: "and anything the contract doesn't mention is assumed hostile."
